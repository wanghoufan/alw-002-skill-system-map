### 1.1 结论①：远端领先本地（A 据此推翻自己 V1.0 的"线上==HEAD"与我 V1.0 的"T2=T3"）

#### 1.1.1 A 的主张

#### 1.1.2 我的独立取证

**证据组 1 · 远端 ref（只读）**

```
$ git ls-remote origin
eb9fbdac3d4ce815c450dc5ff483b02c7d441622    HEAD
eb9fbdac3d4ce815c450dc5ff483b02c7d441622    refs/heads/main

$ git rev-parse HEAD
125e725354288885f667508ba8b1dd9e1dff52f2
```

**两者不同 —— 与 A 完全一致。**

**证据组 2 · 只读 fetch 预演（本轮新增，A 未做）**

```
$ git fetch --dry-run -v origin
POST git-upload-pack (213 bytes)
POST git-upload-pack (980 bytes)
From https://github.com/wanghoufan/alw-002-skill-system-map
   125e725..eb9fbda  main       -> origin/main
```

【事实·实测】`125e725..eb9fbda` 明确给出"本地落后、远端领先"的区间方向。**注意：dry-run 不写本地 ref，已核验 `git rev-parse origin/main` 仍为 `125e725…`。**

**证据组 3 · 我 V1.0 为什么会判错（方法论根源，本轮新增）**

```
$ git rev-parse origin/main
125e725354288885f667508ba8b1dd9e1dff52f2      # ← 与 HEAD 同值，故 origin/main..HEAD 恒为空

$ ls -la .git/FETCH_HEAD
-rw-r--r--@ 1  ...  114  Oct 26 12:22  .git/FETCH_HEAD

$ ls -la .git/refs/remotes/origin/main
-rw-r--r--@ 1  ...   41  Oct 29 17:44  main
```

【事实·实测】本地缓存的 `origin/main` 停在 `125e725`（10-29 17:44 那次 push 后由 git 自动更新），此后远端如何推进，本地**永远不会知道**。`git log origin/main..HEAD` 为空只说明"本地缓存与本地 HEAD 一致"，**与远端无关**。

**证据组 4 · 线上与本地逐文件比对（本轮独立重跑）**

| 文件 | 本地（T2=`125e725`） | 线上（T3） | 差异 |
|---|---|---|---|
| `assets/skills.json` 条数 | 53 | **54** | +1（`secret-scanning`） |

### 4.15 G15｜【新增】本地落后远端，而"线上是不是最新"的判定方法本身就是错的

**① 原来怎么说**
仓库内**从未有过**任何关于"如何核验线上是否与本地一致"的规定。B V1.0 用 `git log origin/main..HEAD` 判定，A V1.0 用 `git rev-list --left-right --count origin/main...HEAD` 判定——**两者都比的是本地缓存的远程分支引用**。

**② 后来实际怎样**
【事实·实测】2026-10-31：

```
git ls-remote origin          → eb9fbdac3d4ce815c450dc5ff483b02c7d441622
git rev-parse HEAD            → 125e725354288885f667508ba8b1dd9e1dff52f2
git fetch --dry-run origin    → 125e725..eb9fbda  main -> origin/main
git rev-parse origin/main     → 125e725…（= HEAD，故 origin/main..HEAD 恒为空）
```

后果：线上与本地**已经是两份不同的事实**，且这个差异**没有出现在任何提交说明、README 或文档里**：

| 项 | 本地 | 线上 |
|---|---|---|
| 清单条数 | 53 | **54** |
| `asOf` | 2026-10-29 | **2026-10-30** |
| 迭代事件数 / 条数 | 26 / 188 | **27 / 190** |
| `index.html` 字节 | 28,910 | **29,167** |
| highlights | 21 | **22** |
| 两张截图 | 2296×5924 / 2296×3200（2.35 MB / 895 KB） | **2300×1495（256 KB / 299 KB）** |

**B V1.0 的额外失误**：§0.2 表格里已经并排写下 T1 = 28,910 B 与 T3 = 29,167 B（**差 257 字节**），却未触发任何追问。

**③ 差在哪里**
差在**"已发布"这个状态从未被纳入验收范围**。所有人的注意力都在"改完文件 + push"，没有人验证"push 之后线上是什么"。而用于验证的命令（`git log origin/main..HEAD`）**在结构上就不可能发现远端更新**——它比的是两个本地引用。

**④ 为何本应提前思考**
"发布"是这类项目的最后一步，也是唯一不可逆的一步。**最后一步必须有一句"怎么确认它成功了"**，否则前面所有验收都是自说自话。而且这个坑极其隐蔽：`origin/main` 在 push 之后会被 git 自动更新，所以这个命令在**自己刚 push 完**时永远正确，只有**别人/别的机器/别的 Agent 推进了远端**时才会失效——这正好是本项目的情形（`eb9fbdac` 显然不是从这台机器推的，或者说推完之后本机没有再 pull）。

**⑤ 不提前会造成何种返工**
- 复盘的形态判断整体跑偏（B V1.0 §0.2 / §6.2 机制五 / §12.1）；
- 更实际的代价：**任何基于"线上就是我刚改的"这一假设做出的决策都是错的**。例如"G8 的 2.35 MB 单图还在线上"——实际线上已经换成 256 KB；而"G2 的 15 个死按钮还在线上"——这个恰好没错，但那是运气不是判断。
- 若终审时才发现，需要额外一轮"把本地拉到远端再重看"的工作。

**⑥ 下次普通人怎么说**
> "改完推上去不算完。**你要证明线上真的是最新的**：不要拿你电脑上'记着的远程分支'来比（那个可能是好几天前的旧快照），要去问远端真正的版本号，或者直接把线上文件下载下来跟你本地的文件比一比。另外，**如果我这边也在别的地方改过，你要先看看远端是不是已经比我新了**，别直接覆盖。"

**⑦ 提前明确的收益**
- 一条命令（`git ls-remote`）或一个文件哈希比对，成本近乎为零；
- 防止"本地落后而不知道"与"远端被覆盖而不知道"两类事故；
- 让"线上形态"成为可验收项，而不是靠猜。

**责任**：**D 主 / C 次**。开发者必须提供可复现的核验方法；顾问必须把它写进验收清单。
**返工分类**：**P（可预防）**。
**当前状态**：❌ `eb9fbdac…` ≠ `125e725…`。

"同一份数据有两个视图"是本项目明确的设计（M11 / 公开版 + 内部版双轨）。既然有两个视图，**就必须回答"两个视图怎么保持一致"**。只回答"内部版不公开"，不回答"内部版怎么同步"，等于把一致性问题藏在了看不见的地方。

**⑤ 不提前会造成何种返工**
- 用户打开内部版时可能在 115 与 53 之间困惑（**尤其是 `skill-internal.html` 没有明显的"已废弃"标记**）；
- 残留文件长期存在，下一轮清理时无法判断"这是最新的还是旧的"；
- 若要恢复内部版，需要先做一次考古。

**⑥ 下次普通人怎么说**
> "我这个东西要两个版本（对外一个、我自己看一个）。**那你要说清楚：内部的那个怎么跟着一起更新？** 别出现'对外的改了、自己的没改'。另外，**被取代的旧版本要么删掉，要么在第一行写上'已废弃，请用 xxx'**，别让它躺在那里骗人。"

**⑦ 提前明确的收益**
一条"两个视图同步清单"或一行废弃标注，避免内部版自身成为第二个不一致源。

**责任**：**D 主（清理与标注）+ U 决策（是否删除）**。**返工分类**：**P（可预防）**。
**当前状态**：❌ `skill-internal.html` 停在 115 项 / 2026-10-26，无废弃标注。

**机制五（改写版）**：

> 也就是说：**远端那次推进是一次"内容增量"（+1 条 Skill、+1 条 highlight、+1 个事件日、换两张图），不是一次"缺陷修复"。**
> **机制五的真正教训**：不是"会不会不一致"，而是**"不一致的时候，没有人把它当成需要解释的信号"**。

**5.3.1 "一次性交付"的结构性成因（V1.0 四条 → V1.1 六条）**

1. 数据驱动型 UI，但数据变更没有触发 UI 回归的意识（G2、G9）；
2. 同一事实散落在 6+ 处（JSON ×2 / HTML 硬编码引用 / JS highlights / README 中英 / PNG / 设计文档），靠人脑同步（G3、G4、G13）；
3. 零自动化，所有一致性只能靠人眼（G13）；
4. 无验收清单，"完成"由执行者自判（§6.1）；
5. **🆕 发布后无核验环节**，"线上是什么"不在任何人的视野里（G15）；
6. **🆕 无"差异必须解释"的纪律**，反证摆在眼前也不追问（机制八）。

六条互为因果：因为没有自动化（3），所以只能靠人脑同步（2）；因为靠人脑同步，所以数据变更容易漏掉 UI（1）；因为没有验收清单（4），漏掉了也没人发现；而**即使有人发现（5、6 提供了机会），也没有纪律把它变成行动**。

### 5.4 方向四（本轮新增）· 本地—远端—线上三处一致性

> 这是 B V1.0 **完全没有的维度**，由本轮修正 1 直接催生。

**5.4.1 三处分别是什么**

| 处 | 是什么 | 本项目的取值 |
|---|---|---|
| **本地** | 工作树 + 本地 HEAD | `125e725`，53 条 / 10-29 / 188 |
| **远端** | GitHub `refs/heads/main` | `eb9fbdac`，**不可直接读取**（不 fetch） |
| **线上** | Pages 部署产物 | 54 条 / 10-30 / 190 |

**5.4.2 三处的两两关系是可以分别断裂的**

| 关系 | 本项目状态 | 判定方法 |
|---|---|---|
| 本地 ↔ 远端 | **断裂**（本地落后） | `git ls-remote` / `git fetch --dry-run` |
| 远端 ↔ 线上 | **未知**（推测线上 = 远端制品）【推断】 | 需 Actions 日志（本轮不访问） |
| 本地 ↔ 线上 | **断裂**（两版不同） | `curl` + `diff` |

**5.4.3 这个方向为什么值得单列**

因为**这三处断裂的方式不同，修复方法也不同**：
- 本地落后远端 → **pull**（但要防止覆盖）；
- 线上落后远端 → **查 Actions 日志**（部署失败？）；
- 本地与线上不同 → **先判断哪个是"对的"，再决定同步方向**。

**而当前没有任何一处有对应的检查。** 这直接导致：任何人（包括下一轮接手的 Agent）打开这个仓库，`git log` 看到的 53 条与浏览器看到的 54 条不一致，**而没有任何文档告诉他以哪个为准**。

### Q11｜【新增】"改完推上去不算完——你怎么证明线上真的是最新的？"

> "改完推上去不算完。**你要证明线上真的是最新的**：不要拿你电脑上'记着的远程分支'来比（那个可能是好几天前的旧快照），要去问远端真正的版本号，或者直接把线上文件下载下来跟你本地的文件比一比、看看里面的日期是不是对得上。另外，**如果我这边也在别的地方改过，你要先看看远端是不是已经比我新了**，别直接覆盖我的。最后，**如果你发现线上和你本地不一样，先告诉我，别自己决定哪个是对的。**"

## 12. 本轮结论、遗留问题与建议

### 12.1 一句话结论（V1.1）

**这个项目的技术实现是合格的，问题出在"开工前没把问题问出来""改数据后没人验证"和"发布后没人核验收"——30 个提交里 18 次是手工数据同步，19 项差距中 9 项主责在顾问侧、8 项主责在开发者侧、3 项必须由用户拍板；所有可预防返工都源于三个缺失：一份写下来的口径定义、一条能自动拦截失配的校验、一次发布后的线上核验。**

**相对 V1.0 的最大变化**：V1.0 认为"问题只在于已发布的版本带着缺陷"；V1.1 确认"**已发布的版本与本地代码已经不同步，且这个不同步无人发现**"。后者不是前者的补充，而是**前者无法被修复的证据**——远端在缺陷产生后又推进了一次，仍未修复任何一个死按钮或死筛选器。
