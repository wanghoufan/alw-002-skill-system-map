## 3. 本轮新增差距证据链（七问逐条）

### 差距 A：死按钮修复选了「补数据」单路径，未做全量复验，8 处残留跨轮存活

1. **原来怎么说**：上一轮 Lessons §3.2/§10 立规——数据集合变更后必须对页面内所有硬编码引用做存在性校验且自动化；B V1.1:276-303 留下 26 行逐条 OK/MISS 清单，照单可全覆盖。
2. **后来实际怎样**：11-01 `49ce7cb`「补齐 16 条可用条目」，把上一轮 MISS 名中的 7 个补回数据（推断，HEAD 内容不可查但 98 名清单实测在列）；本轮实测仍有 8 个唯一名 / 11 处引用 MISS（§2 L2）。
3. **差在哪里**：修复动作是「往数据里补条目」，而不是「先清点 26 处引用、逐条决定补数据还是删按钮」；且没有任何断言验证修复覆盖率，修完即视为完成。
4. **为何本应提前思考**：清单已经摆在 B V1.1 里，修复前逐行打勾是零成本动作；生活区 3 名按新口径（hero-note「只统计中央登记可用」，index.html:32）属 Skill Manager 个人条目（示意稿:3 自述「滴答清单助手与周复盘标准属于 Skill Manager 个人条目」），补数据路径对它们**结构性无效**——选路径前查一下口径就知道补不进来。
5. **不提前造成何种返工**：同一缺陷从 10-29 引入存活到本轮（11-09），跨越两轮复盘；线上（推断仍为 77 项版）18 处死按钮中的 11 处继续对访客必失败。
6. **下次普通人怎么说**：「把页面上每个能点的按钮都点一遍，点完没有一个跳『没有找到』，才算修好。」
7. **提前明确的收益**：26 行清单打勾约半小时，可当场宣布清零或明确宣布「这 8 个是口径性保留」，不必等下一轮复盘再发现残留。

3. **差在哪里**：同一口径变更牵涉三个落点（数据、页面引用、文案），只改了数据一处。
4. **为何本应提前思考**：上一轮 E-024 已经演示过「README 改了、设计文档没改」的自相矛盾页面，译本退出时本应触发「grep 译本名全仓」一次清干净。

7. **提前明确的收益**：口径变更一次闭环，页面与文档不再需要人脑记忆「哪处还没改」。

## 6. 根因追溯（四类，追到机制层）

1. **UI/交互**：死按钮与归零 chip 的表面现象是「数据变了页面没变」，机制根因是流程区 29 处 `data-skill` 与 16 项 `domainOrder` 均为手工硬编码（index.html:44-56、:80），渲染逻辑无条件渲染全部域（:101）、点击行为只是把名字塞进搜索框（:90），整条链路上没有任何一处「名字必须在数据里存在」的约束。不是某人疏忽，是**页面与数据之间没有契约**。
2. **操作体验**：访客点死按钮后的结果是被带回能力盘点显示「没有找到匹配的 Skill」（index.html:110 空态文案）——用户无从区分「这个 Skill 不存在」与「搜索词打错了」，也没有任何死链检测反馈给维护者。根因：空态文案被当作搜索结果问题处理，**未与「引用失效」这一独立故障类别区分**。
3. **外部依赖**：数据真源是仓库外的中央 `SKILL-REGISTRY.md` 与 Skill Manager 清单，地图靠人工抄录（iterations.json:2 自述来源；index.html:75 自述手动更新）。根因：真源在另一个系统里且无导出管道，抄录节奏由人驱动——11-09 抄了最新数据却没提交，正是「人驱动」与「机器驱动」的边界差异（人会停在中途，管道不会）。
4. **质量验证**：全仓零脚本、零测试、CI 只有 deploy job（pages.yml:1-35），「验证」完全等于人眼。根因：上一轮已把三条立规写进 Lessons（存在性断言、空态处理、口径脚注），但**立规落在复盘文档里而不是落在仓库的可执行物里**——文档规约没有转化成 pages.yml 里的一个 job 或一个脚本，规约就只对读过文档的会话生效。
