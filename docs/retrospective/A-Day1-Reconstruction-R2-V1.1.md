## 4. 更新版 Day 1 完整中文提示词（最终版）

以下整段可直接发给执行开发者。

---

我要做一个「Skill 体系地图」网页，把散在各处的技能清单变成一张能看、能查、不会过期的图。下面是我能说清的全部要求；没写的部分你可以合理决定，但凡是涉及「算什么、不算什么」的口径，必须先问我。

### 零、最终要变成什么

一个公开可访问的网页（GitHub Pages），打开就能看到三块：

1. 我的工作与生活是怎么用 Skill 串起来的（流程图）；
2. 我到底有哪些 Skill、分别能干什么（可按领域、来源筛选，可搜索）；
3. 这套体系是怎么一点点长出来的（改进记录 + 迭代热力图）。

另外给我一份内部用的核对材料，记录哪些是真核过的、哪些还没核。

它会增、也会减：Skill 会新增、会升级、会转存档退出分发。页面必须跟得上减少，不能只会上涨。

### 一、它服务谁

- 主要是我自己：一眼看清能力边界，决定下一步补什么。
- 其次是别人：看到链接就能明白我在用什么、怎么用。
- 所以：术语不能只在行内成立，公开页不放内部路径、不放未公开项目的细节。

用户会这样问，请按这个标准做：

- 「我想找个能做 XX 的 Skill，能不能直接搜？」
- 「流程图上的按钮点得动吗？点了会怎样？」
- 「现在到底有几个 Skill，在哪个数字看？」
- 「我加一个新 Skill，要改几个地方？」

### 二、技术形态

- 纯静态：一个 `index.html` + `assets/skills.json` + `assets/iterations.json` + 截图，不要后端、不要数据库、不要构建链。
- 不要引入框架或打包工具；不要新增 `package.json`。
- 手机上要能正常看：单列、不横向滚动、字号不小于 15px，正文基准不小于 19px。
- 首屏不依赖任何外部 CDN；断网时至少能把已加载内容展示出来，加载失败要明确说「加载失败」，不能显示成空列表。

### 三、页面三区

**区 1 · 流程图**

- 分「生活」「开发」两条线，每条线 4–6 个阶段，每个阶段挂 1–4 个 Skill 按钮。
- 按钮上的名字必须能在清单里找到对应条目。找不到的，不许硬写完事——要么换成清单里真实存在的 Skill，要么先问我要不要补进清单。
- 点按钮：跳到清单区、按该 Skill 过滤，并把搜索框填成它的名字。这个行为要真的生效，不能只是滚动。

**区 2 · 盘点表**

- 列：序号、Skill 名称、能力领域、来源、一句话说明。
- 支持按领域筛选、按来源筛选、关键字搜索，三者可叠加。
- 领域筛选按钮只渲染清单里真实有条目的领域；计数为 0 的领域不要显示成 `0` 挂在那里。
- 序号直接用清单里的 id，不要在一次遍历里用 `index+1` 重编——否则删掉一条，后面全部错位，而且你无法解释为什么 76 号不见了。id 有跳号是正常的，显示出来即可。
- 空状态要分级：加载失败、筛选/搜索无结果、引用的 Skill 不存在，三种要给不同的文案与不同的视觉，不能都写成一句灰色小字。

**区 3 · 改进清单**

- 按时间倒序列出每次变更：日期、改了什么、影响哪个数字。
- 上方配热力图或条形图，数据来自 `assets/iterations.json`。
- 图上要有一个口径说明：这个数字数的是什么（是「有日期的变更日志行」，不是「Skill 条数」）。

**通用**

- 清单的数字只在一个地方维护，页面其他位置全部从它派生：条目数、来源分布（自建/官方/社区）、领域计数、页码角的快照日期，都不许手写第二份。
- 页脚那句「数据快照」要读清单里的日期字段，不要写死。写死的兜底值只允许出现在 JS 失败时，并且要能被看出来是兜底。
- 同一句事实只允许有一个权威落点，其余位置是它的派生。凡是「翻译版怎么算」「存档算不算」这类陈述，页面里出现几次就要核对几次。

### 四、数据从哪来

- 真源不在这个仓库：一份在中央 Skill 登记，一份在 Skill Manager 的清单里。这个网页只放抄录结果。
- 所以你必须做两件事：
  1. 抄录时逐条记录「从哪份、哪一天、什么状态」；
  2. 交给我一份对账清单：清单里每一条都能指回真源，真源里每一条要么在清单里、要么写明为什么不在（存档、未分发、非用户级、个人条目）。

### 八、文档与截图

### 九、自动检查（能写脚本就写）

至少四项，`exit code` 非 0 才算失败：

1. 所有 `data-skill` 引用都能在清单里找到，否则列出缺失名字与行号；

做不到脚本化的，就做成一张可勾选的清单文件放进仓库，提交前逐项打勾——不要只活在对话里。

### 十、改完怎么算交付

- 改动当天提交；数据、文案、截图、README 同批，不拆成「明天再补」。

## 6. 验收方法

通用方法（沿用 V1.0）：

- V-1 渲染实测：真开页面，读 DOM 文本与按钮数量，不以「代码看起来对」代替。
- V-2 数据回读：`python3 -c` 直接读 JSON 计数，不引述文档里的数字。
- V-3 线上对照：带时间戳抓线上 JSON，比对 `asOf` 与条数。
- V-4 404 实测：`curl -o /dev/null -w '%{http_code}'` 逐个内部路径。
- V-5 提交对照：`git status --porcelain` 必须干净（除约定的未跟踪目录）。
- V-6 逐字节/逐行比对：文案类改用 `diff`，不只比文件大小。

逐条判据：

| 验收 | 判据 | 命令/方法 |
| --- | --- | --- |
| V-24 | 统计卡数字 = JSON 条数 | 读 `#skillRows tr` 行数 vs `len(skills)` |
| V-25 | 死引用 = 0 或全部有记录 | 正则抽 `data-skill` 求差，差集必须为空或在处置清单里 |
| V-26 | 领域按钮数 = 数据领域数 | 读按钮 `data-domain` 集合 vs `set(s.domain)` |
| V-27 | 三处译本陈述全部一致 | `grep -n '译本\|translated\|translation' README.md README.en.md index.html` 逐条对照数据 |
| V-28 | 序号无重复、无错位 | 抽 `td.num` 文本，与 id 集合比对 |
| V-29 | 内部目录线上 404 | `curl` 三个内部文件 |
| V-30 | 修复路径有书面选型 | 交付说明里必须有覆盖率对比表 |
| V-31 | 三种空态可区分 | 分别制造 404、搜无结果、引用不存在，读文案与样式类 |
| V-32 | 工作树干净且线上同版本 | `git status` + 线上 `asOf` |
| V-33 | 截图同批 | `git show --stat <commit>` 里 PNG 与 JSON 同现；记录条数 |

## 7. 证据缺口与本轮局限

1. **「用户认可 V1」无书面证据**：用户从未对某一版样式签收，只能从 V1 之后连续三次「补数据但不清死引用」推断其关注点在数字。
2. **线上逐字节比对未做**：本轮只比了 `index.html` 的 `size_download`（32290 B）与本地一致，没做 sha256；理论上同尺寸不同内容仍可能。
3. **截图内容未读**：只核了尺寸、体积、提交时间，没 OCR 确认截图里显示的是 98；「截图对应新数据」目前靠提交同批推断。
4. **中央登记真源本轮不可读**：22 条是否真属「漏登」只能从提交信息（`6a3139e` 自述「补齐 22 条可用 Skill」）+ `updated` 日期分布推断，未与中央登记逐条对账（推断）。
5. **死按钮是否有人点过无法判定**：无埋点、无访问日志，不能证明「用户已经踩到」。
6. **B 的 42 提交口径不明**：`HEAD` 与 `--all` 都是 39，无分支无 tag；无法还原 B 的计数来源，只能判定其数值错误。
7. **本轮瑕疵**：
   - N-7 未对 `docs/技能体系示意图.md` 与 98 条逐项比对，只核了总数与日期；
   - N-8 未验证 `assets/iterations.json` 的 `asOf`（2026-11-09）与最大事件日期（2026-11-08）不一致是否会导致热力图缺当日格——只记录该现象，未判定是否缺陷；
   - N-9 未核 22 条新增条目的 `summary` 质量，只核了数量与来源；
   - N-10 未检查 `.gitignore` 中 `/scripts/*` 类忽略条目是否曾误伤过未来要提交的脚本。
8. **需用户拍板的两项**（不拍板则本轮结论保持「待定」）：译本条目今后算不算独立条目；三名个人条目要不要进地图（决定死引用走「补数据」还是「删引用」）。
