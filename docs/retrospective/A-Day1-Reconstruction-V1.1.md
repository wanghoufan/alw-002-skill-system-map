### 1.3 一个必须先讲的方法论教训（本轮自身的教训）

A V1.0 与 B V1.0 都用了 `git rev-list --left-right --count origin/main...HEAD`（或 `git log origin/main..HEAD`）来判定"本地与远程一致"，得到 `0 0` / 空输出，于是都下了"已部署版本 = 已提交版本"的结论。

**这个命令比较的是"本地缓存的 `origin/main` 引用"，不是远端真实状态。** 本仓库 `.git/FETCH_HEAD` 的最后更新时间是 **2026-10-26 12:22**，`.git/refs/remotes/origin/main` 的 mtime 是 **2026-10-29 17:44**——也就是说，本地的 `origin/main` 是 10-29 那次 push 后 git 自动更新的快照，此后无论远端如何推进，本地都不会知道。

【事实·实测】正确做法是 `git ls-remote origin`（只读、不写本地 ref），它返回：

```
eb9fbdac3d4ce815c450dc5ff483b02c7d441622    HEAD
eb9fbdac3d4ce815c450dc5ff483b02c7d441622    refs/heads/main
```

而本地 `git rev-parse HEAD` = `125e725354288885f667508ba8b1dd9e1dff52f2`。**两者不同。**

> **这条教训本身要写进 Day 1 提示词与验收方法**（见 §8.4 V-23）：核验"线上是不是最新"不能用本地缓存的远程分支，必须查远端真实 ref 或直接比线上文件与本地文件的哈希。

# 同样脚本，换成线上两个文件

一、它是什么（定位）

有多少、分哪些领域、从哪来的、在我的工作流里怎么串起来、以及它是怎么一天天长起来的。
这个页面是给别人看的，不是我的工作笔记。

二、技术形态（请严格照做）
- 纯静态：一个 index.html，把 CSS 和 JS 都内联进去，不要引入任何框架、不要 npm、不要构建步骤。
- 数据放两个 JSON 文件：assets/skills.json（Skill 清单）和 assets/iterations.json（变更记录）。

六、统计口径与边界（请在动手前先跟我确认这 9 条，别自己定）

  2. 中文翻译版（比如 xxx-trans-zh）算独立的一条，还是算原版的附属？

  - 你要明白：一个文件一旦被 git 跟踪过，再加忽略规则也没用；

  - 发布到 Pages 用白名单（只发首页 + 数据 + 图片），不要写 path: . 把整个仓库发出去。
  - 仓库里的设计稿、规划稿、复盘记录这类过程文档，不要放在会被发布的目录里。
  - 内部版页面顶部要有一句醒目的提示：这是内部版，不对外发布。
  - 公开版上不要写我们还缺什么能力。
