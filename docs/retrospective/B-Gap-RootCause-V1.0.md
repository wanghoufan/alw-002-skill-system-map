## 3. 差距清单（G1–G14，每项含七问）

> 七问结构：① 原来怎么说 ② 后来实际怎样 ③ 差在哪里 ④ 为何本应提前思考 ⑤ 不提前会造成何种返工 ⑥ 下次普通人怎么说 ⑦ 提前明确的收益
> 责任三类：**U**=用户合理应表达 / **C**=顾问·计划者应主动发现 / **D**=开发者负责解决
> 返工三类：**P**=可预防 / **N**=正常迭代 / **M**=Agent 或流程失误

### G1 「总数」的统计口径从头到尾没有被定义成一条不可变的规则

**① 原来怎么说**
仓库内最早的对外表述（`cce36b9`，10-06）是"查看 Skill 总量、能力领域、来源分布"；`108cd5a`（10-07）第一次写成可核验的规则："统计合并中央 `SKILL-REGISTRY.md` 与个人 Skill Manager 已安装清单，并按 Skill 名称去重"。这句话定义了"两个源取并集、按名去重"，但**没有定义"什么状态的条目算一个 Skill"**。

**② 后来实际怎样**
按 §2.1 的表，同一个"总数"在 23 天内以 75 → 93 → 102 → 111 → 113 → 114 → 115 → 123 → 125 → 126 → 53 的顺序变化。最后一次变化不是增减小，而是**含义反转**：从"登记过的都算"变成"只有可用的才算"，一夜之间 −73。

**③ 差在哪里**
差的不是数字精度，而是**口径这件事本身没有被当成需求来管**。每次更新都由"这次新加了什么"驱动，而不是由"我们的定义是什么"驱动。证据：10-27 `a159140` 的 commit message 是"补齐中央登记 6 条 Skill，地图总数更新至 123"——把"总数"当作一个可以被新条目推动的计数器，而不是一个由定义决定的输出值。

**④ 为何本应提前思考**
"总数"是这个页面最显眼的数字（页面第一屏 stats 第一格、README 第一段、截图里最醒目的位置）。一个展示型页面，**它最显眼的数字的定义**属于必须在动手前钉死的第零号需求。而且这类"资产盘点"天然有一个陷阱：登记量、可用量、分发量是三个不同概念，混用必然翻车。

**⑤ 不提前会造成何种返工**
直接后果：`125e725` 一次性改了 8 个文件、+711 / −1514 行，重算了热力图、领域统计、README 中英两版、并重截三张图。间接后果见 G2（引用失效）、G3（示意稿脱节）、G4（旧口径文案残留）——**这次口径变更是后续三项返工的共同起点**。

**⑥ 下次普通人怎么说**
> "这个页面上最大的那个数字，你帮我数一下：**只算我现在真的能用得上的**。凡是已经淘汰的、只是翻成了中文但还没给智能体用的、或者只是插件自带不算我自己的，都不要数进去。这个规则写成一句话贴在页面边上，以后加东西只能按这句话来数，不能因为我新登记了几个就往上加。"

**⑦ 提前明确的收益**
口径一旦钉死，`125e725` 这次 2000+ 行的返工可以从"一次性大改"降为"日常小步同步"；G2/G3/G4 三项连带返工大概率不存在。

**责任**：**C（顾问·计划者应主动发现，主责）+ U（用户合理应表达，次责）**。理由：用户是领域专家但不是页面需求方，"登记量 vs 可用量"的区别需要顾问主动追问；同时用户作为唯一数据源所有者，应在首次给出清单时说明"这里面有哪几类状态"。
**返工分类**：**P（可预防）**——数据源里"状态"字段缺失是客观限制，但"总数必须有一个写下来的定义"这件事不受此限制，完全可以在 10-06 就写进 README。

**问题 C — 无关文件一并发布**
`path: .` 同时会把 `README.md`、`README.en.md`、`.project.yaml`（含 `local_path` 绝对路径）、`assets/screenshots/`（3.45 MB）等全部发布。其中 `.project.yaml` 包含本机绝对路径 `<工作区>/alw-002-skill 体系地图`（**含真实用户名**，已在 §0.1 声明本报告不复制该路径到外部；此处仅在仓库内部取证语境下指出其存在）。

**③ 差在哪里**
差在**部署范围没有被当作一个需要显式决策的问题**。`path: .` 是最省事的写法，但它等价于"仓库里有什么就发什么"，把"什么该公开"的判断完全交给了 `.gitignore` —— 而 `.gitignore` 是**事后补救**的工具，不是白名单。

**④ 为何本应提前思考**
"公开"是这个项目的既定属性（`visibility: public` + 对外 URL + 中英双语 README）。既然公开，**"发布什么"就应该在第一次配置 CI 时被问一次**。而且这类问题有个特点：一旦配置成 `path: .`，后续所有新增文件**默认都是公开的**，风险随项目增长而单调上升。

**⑤ 不提前会造成何种返工**
22 天的内部材料暴露窗口（未实际发生泄漏，但处于风险中）；`docs/retrospective/` 当前处于"一旦 commit 即公开"的状态——**本轮复盘的两份报告都在这个窗口里**。这是本项目当前**唯一一个可能影响本复盘任务自身**的风险，需在第一轮结束后由用户决策（加 ignore / 改 `path` / 只发指定目录）。

**⑥ 下次普通人怎么说**
> "这个仓库是**公开**的，所以：**哪些东西能发到网上，你先列一个清单**（比如只发首页和它要用的数据文件），按清单来发，**不要图省事把整个文件夹都发出去**。另外，凡是'只给自己看'的内部材料，第一天就放进一个专门的'不上传'目录，别等做完才想起来。"

**⑦ 提前明确的收益**
一次配置决策，永久免疫；避免"内部材料差点上公网"这类不可回滚的事故（**已推送到公开仓库的内容可能被 fork/缓存，删除不等于消失**）。

**返工分类**：**P（可预防）**，且属于**高风险**——泄露类问题不可逆。

### 4.1 首页是否只是"无价值的功能目录"

**结构事实**（`index.html:29–74`）：


**判断**：**不是"无价值的功能目录"**（即不是"点击这里看 A / 点击那里看 B"的导航页）。三块都有实质内容：热力图是真数据、流程图是结构化的、表格是 53 行明细。

> **推断**：`0edd1da` 把 stats 从顶部移到第三部分，可能是为了让热力图成为首屏主角。但这使得"我有 53 个可用 Skill"这个最有力的信息被埋到了页面底部。「待验证」：实际滚动体验是否可接受。

**(b) 三块之间是并置而非递进**。01 持续改进 → 02 工作流 → 03 能力盘点，顺序由 `0edd1da` 确定（`75e6ad6` 之前的顺序是 盘点 → 流程 → 迭代，恰好相反）。**两种顺序都被实现过，且没有留下选择理由**。

### 6.2 六类"看似完成实际未完成"的具体机制

#### 机制一：只测成功路径，异常路径从未走查

**证据**：`load().catch()` 的存在说明作者考虑过"fetch 失败"。但 G2 的失效按钮**不是异常路径，是成功路径**：代码正常执行、渲染正常完成、只是结果是空的。

`renderSkills()` 的三分支中，空态分支（`:110`）**本来就存在且被正确实现**——问题不在空态没写，而在于**没有人意识到这条分支会被"数据变更"触发**。空态在作者心里是"用户搜了个不存在的词"，实际它变成了"数据删了但按钮没删"。

**根因**：**把空态理解为"用户输入错误"的反馈，而没有理解为"数据与 UI 失配"的信号。**

#### 机制二：缺真实样本——用小数据设计的布局，撞上大数据后回炉

**证据链**：
- `cce36b9`（10-06）：54 条数据，表格 `td{padding:13px 14px}`、`domain-tag{white-space:nowrap}`、`.summary{max-width:510px}`（不截断）
- 数据涨到 93 → 126 条
- `d65f3ec`（10-12）"**compact** skill list"：`td{padding:6px 10px}`（**13px→6px**）、加 `table-layout:fixed`、给每列写死宽度（48/260/180/180px）、`.summary` 加 `-webkit-line-clamp:2`（**两行截断**）、`domain-tag` 改 `white-space:normal`、加 `title` 属性兜底

**这是一次典型的"数据量变化引发的布局回炉"**。初版在 54 条下看起来没问题，126 条下表格过高、标签换行失控，于是压缩。

**根因**：**没有用"最大预期数据量"做设计验证**。而这个项目的最大数据量是可预见的——Skill 只会越来越多。

#### 机制三：未覆盖异常——外部依赖的失败路径零测试

**证据**：`iterations.json` 的 `countDefinition` 写着"有日期的变更日志行数量"，说明作者知道源数据格式不规整（`docs/技能体系示意图.md:69` 自己也写了"历史记录的粒度和日期格式不完全一致"）。

但页面对以下异常**没有任何处理**：
- `events` 里有非 2026 年的日期 → 会被静默忽略（`counts[iso]` 查不到就当 0）
- `events` 里有重复日期 → `Object.fromEntries` 后者覆盖前者，**总数会算错**
- `skills.json` 里有 `domain` 不在 `domainOrder` 里的条目 → **该条目只能通过"全部"看到，无法通过领域筛选找到**（当前恰好无此情况，已验证：0 个 orphan）
- `skills.json` 里 `id` 重复 → 表格序号重复

**根因**：**只有"数据正确"这一种假设，没有"数据可能不干净"的检查。**

#### 机制四：未做多端——唯一断点是靠猜的

**证据**：`@media(max-width:760px)` 是唯一的响应式断点，处理了：`.wrap` padding、`.top` 高度、导航间距、hero 单列、stats 两列、`.toolbar` 竖排、`.recent` 两列、`.foot` 竖排。

**未处理**：
- 表格：仍是 `min-width:900px` + 横向滚动（未做卡片化/列隐藏）
- 工作流：`.flow{min-width:1030px}` + 横向滚动（6 个 168px 卡片，手机上要滑很久）
- 热力图：`.heat-scroll{overflow:auto}`，53 周 × 16px ≈ 848px，手机上也要横向滚动

**也就是说：移动端有 3 处横向滚动容器（表格、工作流、热力图），页面主体在手机上基本靠横向滑。**

**根因**：**"响应式"被理解为"加一个断点改字号"，而不是"逐块确认窄屏可用性"。**「待验证」：实际手机观感。

#### 机制五：已发布版本与本地代码不一致——**本项目此项不成立，但值得记录判定过程**

取证结论（§0.2）：**T1 = T2 = T3，三者一致**。判定依据：
- `git status --short` 无 `M`/`D`
- `git log origin/main..HEAD` 为空
- 线上 `curl` 取源：`data-skill` 26 个（与本地一致）、"总数到 126" 1 处（与本地一致）、hero 文案为新版、stats 标签为"可用 Skill"

**这一点必须明确写出，因为它改变了根因方向**：本项目的问题**不是**"本地改好了没发"，而是"**发上去的版本本身就是带缺陷的**"。这两者的修复路径完全不同——前者改流程（发布纪律），后者改验证（发布前检查什么）。

#### 机制六：验收口径不明——"完成"没有可勾选的定义

**证据**：30 个提交的 message 里，描述"完成"的用词有："publish"、"add"、"refresh"、"同步"、"补齐"、"更新"、"对账"、"重算"。**没有一次提到"验证过 XX"或"检查过 XX"**，除了 `local-only` 里提到"地图已推送并在线核验"（核验的是"推送成功"，不是"内容正确"）。

**根因**：**没有一份"发布前要做什么"的清单**。若有，G2 的"点一遍所有按钮"必然在列。

### 6.3 "一次性交付"的结构性成因

综合以上六条，本项目"看似完成实则返工"的结构性成因有四条：

1. **数据驱动型 UI，但数据变更没有触发 UI 回归的意识**（G2、G9）
2. **同一事实散落在 5+ 处（JSON / HTML 硬编码数组 / JS highlights / README 中英 / 截图 / 设计文档），靠人脑同步**（G3、G4、G13）
3. **零自动化，所有一致性只能靠人眼**（G13）
4. **无验收清单，"完成"由执行者自判**（§6.1）

**这四条互为因果**：因为没有自动化（3），所以只能靠人脑同步（2）；因为靠人脑同步，所以数据变更容易漏掉 UI（1）；因为没有验收清单（4），所以漏掉了也没人发现。

> "流程图里每个小按钮点一下，都要能跳到下面清单里对应那一行，**并且那一行要有内容**。你做完**把每个按钮都点一遍**；跳过去是空的，就说明这个按钮指向的东西已经不在清单里了——要么删按钮，要么把东西加回来。**以后每次改清单，都要再点一遍。**"

## 12. 本轮结论与移交建议

### 12.1 一句话结论

**这个项目的技术实现是合格的，问题出在"开工前没把问题问出来"和"改数据后没人验证"——30 个提交里 18 次是手工数据同步，13 项差距中 9 项主责在顾问侧，而所有 13 项可预防返工都源于两个缺失：一份写下来的口径定义、一条能自动拦截失配的校验。**

### 12.2 给第二轮（交叉验证）的四条待确认事项

1. **T4（用户最终认可版本）是否存在于仓库之外**——本轮在仓库内未找到任何验收记录，需在第二轮通过访谈确认：用户是否实际打开过页面？是否点过流程按钮？是否知道 126 与 53 的变化？
2. **125e725 的口径变更是否经过用户确认**——commit message 写"公开版与内部版同步改为只统计「可用」"，但未记录是谁决定的。
3. **`docs/retrospective/` 的公开发布风险需用户决策**——本目录一旦 commit 即通过 `path: .` 发布到公开 Pages。建议在第一轮结束后立即决定：加 `.gitignore` 条目 / 改 `pages.yml` 的 `path` 为白名单 / 将复盘文档移到仓库外。**本轮未做任何修改（遵守硬边界）。**
4. **G2 的 15 个失效按钮是否为已知问题**——若用户已知并接受，则降为"待办"；若未知，则应立即修复（修复成本极低：改 HTML 或从数据生成）。
