## 1. 最初目标、当前已核实状态、覆盖度与证据缺口

### 最初目标
做一个可公开访问的 Skill 体系地图页面，把分散在各处的 Skill 登记成一张可浏览、可筛选的地图。

### 当前已核实状态：**四态不一致，且线上版本领先本地**

| 形态 | 事实 | 证据 |
|---|---|---|
| 本地 HEAD | `125e725`，53 条，`asOf` 2026-10-29，迭代 188 条 | `git rev-parse HEAD`、`skills.json` |
| **远端 origin/main** | **`eb9fbdac…` ≠ 本地 `125e725`** | `git ls-remote origin`、`git fetch --dry-run` → `125e725..eb9fbda` |
| 线上（GitHub Pages） | 54 条，`asOf` 2026-10-30，迭代 27 事件 / 190 条，highlights 22，两张截图改为 2300×1495 | 线上 HTTP + PNG IHDR |
| 用户最终认可版本 | 未书面确认 | 无 |

**两路共同的重大修正**：A V1.0 的「线上 == HEAD」与 B V1.0 的「T2 == T3」**均被推翻**。根因是两路都用本地缓存的 `origin/main` 判远端——实测本地 `origin/main` 恒等于 HEAD（`125e725`），`.git/FETCH_HEAD` 停在 10-26，`git log origin/main..HEAD` 必然为空。

### 当前活缺陷（线上与本地同时存在）
1. **15 个死按钮 / 18 处死引用**：`index.html` 流程区 29 个 `data-skill` 引用中，18 处（15 个唯一名）指向已被 `125e725` 移除的 Skill，点击即"没有找到"。线上版本完全相同。
2. **5 个死筛选器**：`domainOrder` 16 个领域中 5 个当前计数为 0 仍渲染成可点击 chip（实际渲染 17 个，`index.html:101` 另拼了"全部"）。

### 覆盖度
- 30 次提交全量可读，单分支，工作树干净。
- 全 28 个历史版本做过引用/归零域回归：前 27 版**零失效**，仅 `125e725` 崩——即两个缺陷是同一次提交引入的、全新出现的问题，而非长期存在。

### 证据缺口
1. 用户最终认可版本无书面确认。
2. 线上与本地的 `index.html` 差异仅一行 highlights，其余未逐字节比对全部资源。
3. `docs/技能体系示意图.md` 的泄露范围只做了 HTTP 层面核实，未评估搜索引擎/缓存/ fork 的扩散面。

## 3. 可预防返工 Top 5

### 3.1 已发生的不可逆泄露 —— 最高优先级
`pages.yml:31` 用 `path: .` 把**整个仓库**发布到 GitHub Pages；`docs/retrospective/` 至今不在 79 行 `.gitignore` 中。
**已泄露事实**：`docs/技能体系示意图.md` 线上 HTTP 200（12,418 B），含 126 个编号条目、127 个反引号 token、2 个中文别名，还暴露仓库外数据源规模（中央 106 / SM 107 / 101），可推算未公开量。
**待用户拍板（须在下一次 push 前）**：①`docs/retrospective/` 三选一（加入 `.gitignore` / 改用 `path` 白名单 / 迁出仓库）；②示意稿三选一（下线 / 脱敏 / 接受已公开）；③`path: .` 是否改白名单。**本轮只记录，未做任何修改。**

### 3.2 改数据没改引用
口径变更删掉 73 条数据，却没检查流程图里 26 个硬编码名字还剩几个有效 → 15 个死按钮。全 28 版回归证明：前 27 版引用一直 100% 有效，这是**唯一一次**破坏。
**下次做法**：数据集合变更后，必须对页面内所有硬编码引用做一次存在性校验，且要成为自动化断言，不能靠人眼。

### 3.3 「总数」定义没钉死
最显眼的数字 23 天换了 5 次含义（75→…→126→53），最后一次一夜 −73，连带重算统计、重截三张图、改两份 README 共 2000+ 行。
**下次做法**：Day 1 就要问死「这个数字是全量并集，还是只算可用？」并把口径定义写进数据文件本身。

### 3.4 零自动化校验 + 同一事实散在 5 处靠人脑同步
18 次手工同步、每次改 6 处，而设计文档自己两次写了"自动生成"却从未落地，导致没有任何机器能发现数字打架或引用失效。口径变更后 README 和统计卡改了，设计文档仍写 126、JS 更新文案仍写 123/124/126。
**下次做法**：单一数据源 + 生成脚本，是这类"展示型索引"项目的第一优先级，不是优化项。

### 3.5 公开范围没有白名单，边界 22 天后才显性化
立项时无私有隔离，10-28 才把 `/local-only/` 进 `.gitignore`。属不可逆的边界问题，Day 1 一句话即可问出。
补充：点文件（`.project.yaml`、`.gitignore`、`.github/*`）实测 404，未被发布——但这是**默认行为、仓库内无一行声明**，属"运气不是设计"。

## 6. UI / 布局 / 高频操作的可复用经验

1. **索引类页面的"筛选器"必须有空态处理**：计数为 0 的领域 chip 不应渲染成可点击，否则等于给用户一个必失败的入口。
2. **硬编码的名称引用是定时炸弹**：任何"从数据集里挑名字写进页面"的写法，都要配套存在性校验。
3. **最显眼的数字必须有口径脚注**：总数旁边写清"统计范围与截止日期"，比事后解释便宜得多。
4. **同一事实不要散在 5 处**：README（中/英）、统计卡、设计文档、JS 文案——任一处漏改就是自相矛盾的页面。
5. **"全部"这类聚合项要计入渲染数**：本次 16 域渲染成 17 chip，导致计数对不上，排查成本被放大。

## 9. 适用范围、反例与"不能推广为通用规则"的部分

- **适用**：公开托管的静态索引/地图/目录型项目；单一数据集驱动展示页；有公开/内部双轨的材料仓库。
- **反例 1**：不要把"必须自动生成"推广到一次性、数据量极小的页面——手工同步 5 条数据是合理的。判据是同步次数与每次改动处数（本项目 18 次 × 6 处，明显越界）。
- **反例 2**：不要把"`path: .` 一定错"绝对化——纯公开仓库用 `path: .` 没问题；错在**混合了私有材料却仍全量发布**。
- **反例 3**：`.gitignore` 对已跟踪文件无效，本项目 `/local-only/` 生效是因为它**从未被跟踪**；换一个已被跟踪的目录，加 `.gitignore` 不解决问题，必须 `git rm --cached`。
- **不可推广**：`.project.yaml` 等点文件未被发布是 Pages 的默认行为，不能当作"已配置安全边界"。
- **方法学**：差异必须先解释。B V1.0 曾把 T1（28,910 B）与 T3（29,167 B）的 257 B 差异并排记下却未追问，差点漏掉"线上领先本地"这个关键事实。
