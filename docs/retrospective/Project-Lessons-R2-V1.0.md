## 4. 可预防返工 Top 5

1. **没有对账脚本**：真源在仓库外（中央登记 + Skill Manager 清单），`assets/skills.json` 只是抄录产物，没有任何程序能告诉你「登记了但没进地图」。所以正确的 Day 1 要求是「先有对账脚本，再有地图」。这一条能同时消掉 G-G、G-I、G-F。
2. **完成定义不含「已提交」**：本轮 B 路最大误判就来自「工作区改了包没提交」，反过来看，这也说明项目本身没有「改完必须提交并回读线上」的硬规则。
3. **死引用没有回扫**：`index.html` 里 8 个名字是写死的，删条目前不扫就会留 11 处死链。这一条需要一行脚本（数据里没有的 `data-skill` 全打印），却是跨三轮未修的唯一缺陷。
4. **数字手写**：`77+22=98` 这类算不平的表述、README 里的条目数、`docs/技能体系示意图.md:3` 的「126 项 / 2026-10-29」，全部是手写。数字必须由 `assets/skills.json` 现算。
5. **公开面与内部面不分目录**：`pages.yml:31` 的 `path: .` 会把整个仓库发布出去，复盘、`docs/`、`temp/` 一并公开。Day 1 若说清「只发布 `site/`」，`docs/retrospective/` 是否入库就不需要每次开会讨论。

## 5. 正常演化（不能用事后知识否认）

- 53 → 57 → 73 → 75 → 76 → 77 → 98 的阶梯，是「登记持续发生、地图按巡检节奏补齐」的正常形态。要求 Day 1 就做到实时同步，需要先建中央仓库直连，这在当时不具备条件。
- 11-09 一次性 +22，是补齐积压，不是当日产出暴增。把它当「产出效率高」会得出完全相反的管理结论。
- `docs/技能体系示意图.md` 停在 126 项 / 2026-10-29，是「示意图」这类非核心文档的正常腐化，不属缺陷，但需标注口径日期。
