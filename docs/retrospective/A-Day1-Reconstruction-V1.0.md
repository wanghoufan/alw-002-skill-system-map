## 0. 本报告的用法与可信度边界

这份报告回答一个问题：**如果今天从零重新立项 `alw-002-skill 体系地图`，一个普通用户在 Day 1 应该向云端计划者说什么，才能尽量少返工。**

它不是"重构方案"，也不是"事后诸葛亮式的需求清单"。为了避免后者，本报告对每一类结论都打了标记：

| 标记 | 含义 | 读者应如何使用 |
| --- | --- | --- |
| **【事实】** | 可由仓库相对路径 + Git hash + 日期 + 文件/行号重定位的客观存在 | 可直接引用 |
| **【推断】** | 由事实组合推出的判断，Git 提交说明不足以单独证明 | 需结合 B 路用户侧证据交叉验证 |
| **【不可避免】** | 属于真实迭代中"当时无法预见"的部分，事后知识不能否认当时的不确定性 | **不得**写进"Day 1 就该说清楚"的需求 |
| **【可提前】** | 属于 Day 1 用一句大白话就能说清、说了就能省掉后续返工的 | **必须**写进 Day 1 提示词 |

**一条重要的取证纪律**：Git 提交说明只能证明"某次变更被记录了"，**不能自动证明用户为何提出该变更**。例如 `125e725` 的说明写着"地图口径改为只统计可用 Skill，总数 126→53"，这只能证明口径变更这件事发生了；它为什么发生、是用户主动要求还是管家巡检发现，单靠提交说明无法定论。本报告在涉及"动机"处一律标【推断】。

### 2.5 三件必须分开的东西（治理/索引工程的特有风险）

任务书要求区分"地图内容 vs 承载脚本/生成器 vs 配套仓库"。本项目的实际情况是：

**(a) 地图内容**：`assets/skills.json`（53 条）+ `assets/iterations.json`（188 条）+ `index.html` 内嵌的 21 条 `highlights`。

**(b) 承载它的脚本/生成器**：**不存在**。
【事实】`git log --pretty=format: --name-only --all | sort -u | grep -E '\.(sh|py|js|ts)$'` 返回空 → **本仓库历史上从未出现过任何脚本文件**。
【事实】`index.html:84` 用 `fetch('./assets/skills.json')` 与 `fetch('./assets/iterations.json')` 读数据；页面本身是纯静态、无构建、无框架、无 npm。
【推断】`skills.json` 是**人工（或由智能体执行 `skill-map-maintainer-local-zh` 后）逐条编辑**的产物，不是脚本生成。证据：
- 文件内 JSON 缩进风格在历史中变化过（`125e725` 对 `iterations.json` 做了整文件重排版，110 行全改，内容不变）；
- 部分条目 `"id"` 字段在对象开头（id 1–38, 49–53），部分在末尾（id 39–48），是典型的手工/增量编辑痕迹；
- `index.html:122` 的 `highlights` 数组是**硬编码在 HTML 里的**，不在 JSON 中——每次更新"近期更新"都要改 `index.html` 本身。

**(c) 配套仓库**：
- **数据源**：中央 `SKILL-REGISTRY.md` + 本机 Skill Manager 已安装清单，二者都在本仓库之外（`README.md:35`）。
- **维护流程的承载方**：`skill-map-maintainer-local-zh` 这个 Skill 不在本仓库内（`assets/skills.json:381-389` 只登记了它的一条记录，内容为"核对中央登记与 Skill Manager，维护公开地图和私有体检版；本用户的公开地图变更默认完成提交、推送、部署和线上核验，且不公开内部体检材料"）；在配套治理仓库 `000-alw-个人偏好-电脑治理仓库-skill管理` 中被引用（匹配到 `Skill 管家/说明.md` 等 5 处）。

**这一区分对 Day 1 提示词的直接影响**：如果 Day 1 只说"做一个 Skill 地图网页"，计划者 100% 会做成一个"读取本地列表并渲染"的自包含小应用；而真实形态是"一个**人工对账流程**的展示端"，真正的成本在对账与口径治理，不在页面。这是本次复盘最有价值的一条反推。

## 4. 关键 UI / 操作模式（成熟形态沉淀出的"必须这样"）

### 4.1 单文件静态页 + 两个 JSON，无构建

【事实】`index.html` 内嵌全部 CSS（`<style>`，`index.html:9-21`）与 JS（`index.html:77-126`）；外部依赖只有两个 `fetch`。CI 是 `upload-pages-artifact` with `path: .`，**没有任何 build 步骤**（`pages.yml:31-33`）。
【事实】全仓库历史无 `.sh/.py/.js/.ts` 文件。

**意义**：这是"能给人看的展示页"最省心的形态——改一个 JSON 就生效，push 即部署。**Day 1 应直接指定这个形态**，不要让计划者引入框架。

### 4.2 三个分区的固定顺序：持续改进 → 工作流 → 能力盘点

【事实】由 `0edd1da` 定稿，之后再未变动（`index.html:27` 导航、`index.html:34/40/60` 三个 `<section>`）。

【事实】来源（4）× 领域（16）× 搜索（name+summary+source），且领域 chip 的计数**跟随当前来源筛选**重算（`index.html:99-101`：`relevant = allSkills.filter(s => activeKind==='全部' || s.kind===activeKind)`）。

【事实】结果计数文案格式：`${kindLabel} · 显示 ${list.length} 项`（`index.html:109`），在 `20c9034` 由原"显示 X / Y 项"改来。


## 10. A 路 V1.0 的三条核心判断（供 B 路交叉）

> 这三条是本轮取证中**对 Day 1 提示词影响最大**的判断，且都可以被 B 路的用户侧证据证伪或加强。

1. **本项目的真实成本不在页面，在"对账与口径治理"。**
   30 个提交中，只有 8 个是页面/UI 相关（`20c9034`–`108cd5a` 段），其余 22 个都是"数据同步 + 文档同步 + 截图同步"；仓库内**从未出现过任何脚本**，说明维护靠的是人工流程（或智能体执行 Skill）而非自动化。若 Day 1 只说"做个地图网页"，计划者会交付一个自包含小应用，而用户真正需要的是一个**低成本可维护的展示端**。

2. **"总数怎么算"是本项目唯一一次真正的破坏性返工，且它在 Day 1 完全问得出来。**
   `125e725` 一次删掉 73 条、改 3 份文档、重截 3 张图（711 增 / 1514 删）。根因不是技术实现，而是立项时没定死口径（全量并集 vs 只算可用）。**注意**：中央登记表长出"状态"列这件事本身是不可避免的（U1），但"口径要定死、改口径算破坏性变更"这条约定是 Day 1 就能立的。二者不可混淆。

3. **"公开版 / 内部版双轨"是隐含需求，22 天后才显性化，但 Day 1 一句话就能问出来。**
   立项（10-06）时没有任何私有隔离；到 10-28（`7ed2bd4`）才把 `/local-only/` 写进 `.gitignore`；内部版横幅、maintainer summary 两处都强调"不公开内部体检材料"。这是本项目**安全边界**层面的要求，属于一旦泄露不可逆的类型，必须在 Day 1 问清。
